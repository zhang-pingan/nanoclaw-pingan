概括

MixClaw 的核心结论是：Agent 能力必须被工程化。它不是单个聊天窗口， 而是一套具备状态、权限、隔离、恢复、评估和审计能力的个人 Agent 操作系统。

定位 个人 Agent 操作系统

工作台、助理、移动端和企微只是入口，最终都收敛到同一套宿主机状态。

边界 控制面与执行面分离

宿主机保留状态、权限、凭证和审计；容器只承担受控工具执行。

流程 状态机驱动交付

需求、修复、部署、测试都被建模为可 checkpoint 的 durable workflow。

质量 Harness 化 Agent

标准输入、结构化输出、Trace、产物契约、评估器和失败分类共同约束交付。

核心模块介绍

MixClaw 的模块边界很明确：入口层负责交互，宿主机负责控制，容器负责执行， Workflow 负责把执行结果推进成可审计的工程交付。

系统架构分成两层：Agent Loop 负责智能执行，Agent Runtime Infrastructure 负责让执行可运行、可恢复、可追踪、可审计。

Agent Runtime Infrastructure

Runtime 的目标不是“让 Agent 能调用工具”，而是把每次执行变成可启动、可约束、可恢复、 可评价的工程单元。这里的 Harness Engine 不是单纯的容器包装，而是把模型调用、工具面、沙箱、输出协议、 Trace 和评估串成一次可复现 run 的执行层。

类 LangGraph 架构

状态机 + checkpoint + interrupt

MixClaw 已在宿主机实现 workflow state、durable checkpoint、pending interrupt、resume attempt、workflow event、outbox 和 watchdog。它类似 LangGraph 的地方在于：状态可持久化， 节点可恢复，副作用可重试，人类输入是一等节点。

为什么不直接用 LangGraph

Claude 已承担内层 Agent Loop

当前系统已有状态机、checkpoint等langGraph核心机制；内层 Agent Loop 又由 claude 执行。直接引入 LangGraph 会带来额外适配成本，而收益不如保持现有 TypeScript runtime 统一。

Harness Engine 输入

统一单次运行的输入契约

宿主机把 prompt、sessionId、model、runId、queryId、groupFolder、workflowId、 stageKey、delegationId 等元数据收束成一次 run 的标准输入。

Agent-Computer Interface

让 Agent 真正碰到受控系统

容器 runner、挂载目录、占位凭证、MCP、Skill 和 hooks 组成专用 ACI；SWE-agent 的结果也说明，接口设计会直接影响 Agent 完成代码编辑、仓库导航和测试执行的能力。

Trace / Eval

输出先结构化，再进入评估

固定 marker、success/error/event 解析、Trace、failure taxonomy 和阶段评估一起工作；OpenAI 的 agent evals 和 trace grading 也把运行记录当成可评分、可回归的对象。

Workflow 详解

Workflow 的重点不在具体配置字段，而在抽象层。MixClaw 通过节点、待处理输入、卡片和 steps 四类抽象，让新工作流可以快速拼装， 而不是重写 runtime。

节点抽象化 待处理输入抽象化 卡片抽象化 steps 抽象化

节点只分 delegation、interrupt、system、terminal 四类。 新工作流只需要决定每个阶段属于哪种节点，而不是重新设计整个 runtime。

快速新建新的工作流 只要组合抽象
从需求到交付 从修复到验证 从审批到恢复

新流程的差异主要体现在角色、卡片、契约和评估策略，节点引擎保持稳定。 这是 MixClaw 能快速扩展新流程类型的基础。

低成本复用 统一审计与恢复
节点抽象化 每个节点只定义自己的职责和迁移规则，避免把业务逻辑散落到 runtime 代码里。
待处理输入抽象化 审批、补充输入、凭证和外部阻塞都统一成 interrupt，不再拆成多个临时模型。
卡片抽象化 卡片只是交互外壳，真正的业务语义通过 resume action 和 payload schema 表达。
steps 抽象化 system / before_delegate / after_complete 都是在编排可注册 handler，复用方式一致。

新建工作流路径

1
定义阶段 决定每个阶段是 delegation、interrupt、system 还是 terminal。
2
挂接卡片与动作 让待处理输入通过卡片和 resume action 进入同一恢复链路。
3
复用 steps 用统一 handler 注册表拼装 system 任务、前置检查和后置整理。
4
得到新工作流 不用重写 runtime，只新增 definition，就能生成新的 workflow 类型。

dev_test

从方案设计开始，经过方案审核、开发、开发复核、预发部署和测试验证。 角色包括 planner、plan_examiner、dev、dev_examiner、ops、test； 支持从方案、开发或测试前确认入口进入。

Bug 修复测试流程

fix_test

从 Bug 修复开始，进入预发部署和测试验证。测试失败时进入复修 Round， 再次部署和验证；部署失败、通过、取消等状态进入 terminal。

Resume 的事务边界： resumeWorkflowInterrupt() 在同一事务内完成幂等检查、interrupt 状态校验、action/channel/schema 校验、mark resumed、写 resume attempt、写 event、合并 context patch、apply transition 和 checkpoint。通知、卡片刷新、工作台同步等副作用走 outbox。

Harness Engine

MixClaw 把 Agent 输出从“自然语言回答”升级为“有契约、有证据、有评估、 有追踪的工程交付”。

Typed Handoff 每次委派附带输入/输出 schema、成功标准和 artifact contract。
Artifact Contract 约束交付字段、文件路径、front matter、大小和允许目录。
Stage Evaluation 阶段评估输出 passed、needs_revision、failed 或 pending。
Failure Taxonomy 区分模型、工具、沙箱、配置、权限、超时、测试或部署失败。
Trace & Workbench Query、Step、Event、产物、时间线和待办统一展示。

个人助手详解

个人助手是 MixClaw 的 Agent 主动层。它会根据配置的关注点主动的扫描今日计划、工作台、定时任务、Agent Runs 和线上日志等信息， 把需要关注的事汇总到 Agent Inbox，并在策略允许时自动排查、 自动处理低风险待办、准备修复或进入受控自我进化。

扫描触发源 Proactive Engine 按配置扫描今日计划、未完成计划、工作台任务、 定时任务失败、Agent 执行异常和线上 error 日志。
生成 Inbox 发现的问题通过 dedupe key 汇总成 Agent Inbox，带上来源、 优先级、动作入口和上下文，避免重复提醒。
提醒与触达 桌面助理、Web 工作台和飞书卡片共享同一待办状态，支持查看、 稍后、忽略、完成、排查和修复。
自动排查 对失败、卡住、日志异常等事项启动容器 Agent 主动取证， 输出根因、影响面、证据和可修复分组。
受控执行 对可自动处理的工作台待办可生成表单、审批建议或执行动作； 对可修复分组可发起修复，但保留策略和审计边界。
同步闭环 每个动作写入 action log、Trace、Inbox extra 和工作台状态， 结果可追踪、可回看、可继续处理。
计划自动化 发现当天计划缺失和往日未完成

助手会把“今天还没有计划”“历史计划还有未完成项”转成待办， 提醒用户继续计划或补充安排；针对服务 coding 异常，还可以结合代码、 工作台任务和执行记录生成异常候选。

工作台自动化 处理待审批、待补充和卡住任务

对 pending action item，助手可主动读取任务上下文、产物和卡片 schema，生成可提交的表单内容或审批决策；对失败、取消、长时间无进展的任务， 可发起原因分析并提出下一步。

执行异常自动化 排查 Agent Runs 和定时任务失败

当容器退出、超时、模型输出异常、定时任务失败或 trace 中断时， 助手能启动调查 Agent 读取运行记录、源码和最近变更，判断是环境、 代码、提示词、权限还是数据问题。

线上日志自动化 扫描服务 error 日志并归因

助手按服务配置读取线上 error 日志，使用日志分组规则聚合错误， 将异常映射到服务、主机、日志路径和时间窗口，再生成可调查或可修复的 Inbox。

修复自动化 从调查结论推进到受控修复

调查结果标记 repairable 后，助手可按分组运行修复 Agent， 让 Agent 基于证据修改代码、执行检查并输出修复结果；失败时保留 next action， 成功时把待办推进到完成状态。

自我进化自动化 持续发现自身优化方向

Evolution Engine 可定时选择优化方向、生成方案、评估风险、 创建工作分支、实现、检查、复核并等待采纳。默认不自动实现、不自动合并主分支， 适合把助手自身能力小步提升。

策略控制

主动性可以逐项打开

AssistantSettings 控制 enabled、quiet / balanced / active 主动等级、扫描间隔、静默时段、触发规则、服务范围、 investigationEnabled 和 autoEnabled。默认值保持保守： 自我进化关闭，自动实现和自动采纳关闭，触发规则的自动处理也默认关闭。

安全边界

主动不是越权执行

助手的主动动作仍通过宿主机状态、容器隔离、工作台动作路由、 action log、Trace 和 Inbox 状态管理；高风险操作回到用户审批， 低风险自动化也必须留下来源、输入、输出和结果记录。

个人助手的产品价值： 它把“用户想起来才处理”变成“系统发现后主动推到用户面前”，再把 “提醒用户”升级为“在可控范围内先取证、先准备、先处理”。因此它既是提醒中心， 也是工作台自动化入口、故障排查入口和自我改进入口。

核心优势

这些优势基本对应 TECHNOLOGY.md 的主线：安全隔离、Agent 蜂窝架构、harness 工程、记忆与知识库、 workflow 机制和可审计交付。

安全性

容器化沙箱与凭证代理

高权限执行放在容器内，真实密钥留在宿主机；挂载白名单、会话隔离和 IPC 授权把风险收紧到明确边界。

Agent 蜂窝架构

主调度与角色 Agent 分离

宿主机统一调度 planner、dev、reviewer、ops、test 等角色，避免多个 Agent 共用一个混乱上下文池。

Harness 工程

让 Agent 可运行、可观测、可评估

统一输入、统一执行环境、流式输出解析、产物契约、阶段评估和失败分类，构成完整工程闭环。

记忆与 Wiki

结构化记忆 + 可引用知识

MixClaw 不只存对话历史，还把长期偏好、项目知识、证据链和关系图分开建模，减少上下文漂移。

Workflow 抽象

快速拼装新流程

节点、pending input、卡片和 steps 都是可复用抽象，所以新工作流可以低成本快速创建，而不是复制 runtime。

交付审计

Trace、事件和回放

每次执行都沉淀 Query、Step、Event、产物、评估结果和错误分类，便于复盘和继续推进。

扩展与演进

项目的扩展点围绕“新增入口、新增流程、新增能力、新增知识”展开， 避免把所有变化塞进单一主流程。

新增频道

Channel Registry

实现 Channel 接口，模块加载时注册 factory；凭证缺失时返回 null。

新增流程

Workflow Definition

新增 roles、entry_points、states、cards、artifact contract 和 evaluator。

新增技能

Container Skill

用 container/skills 固化角色方法论，权限仍由宿主机和容器边界控制。

新增步骤

Action Handler

通过 registry 注册 WorkflowActionHandler，即可被 system/hook steps 调用。
